# 修复详解

共 7 处，涉及 6 个源文件。每条都注明实测依据 —— 排查过程中有若干推断被实验推翻，
末尾「走过的弯路」如实记录，以免他人重蹈。

---

## 1. use-after-free（段错误主因）

`src/infocenter.c` · `update_storage_from_script()`

```c
const char *stopped_at = tokenize_and_store(out, '\n', stores, store_len);
free((void *)out);                            // ← 先释放
return *stopped_at == 0 ? SUCCESS : FAILURE;  // ← 再解引用
```

`stopped_at` 是指向 `out` 缓冲区**内部**的游标，代码却先 `free(out)` 再读它。

**为何偏偏在新固件上必崩**：缓冲区固定 65536 字节。新版 musl 对该尺寸走 `mmap`，
`free()` 时直接 `munmap` **把整页交还内核**，地址随即不可访问 → SIGSEGV。
旧 musl 留在堆内，读到垃圾值但不触发异常，于是 bug 潜伏多年。

修复：在 `free()` 之前取值。

## 2. 缓冲区从不写终止符

`src/scripts.c` · `script_get_output()`

```c
ret = (char *)malloc(SCRIPT_OUTPUT_BUFFER_SIZE);   // 65536，未初始化
if (ret < 0) { ... }                               // 指针比大小，恒不成立
fread(ret, 1, SCRIPT_OUTPUT_BUFFER_SIZE, fp);      // 读满整个缓冲区
return ret;                                        // 从未写入 '\0'
```

返回值被调用方当作 C 字符串交给 `strchr()`/`strlen()`，越过 64KB 边界继续扫描未初始化内存。
另 `malloc` 失败返回 `NULL` 而非负数，原判断无效。

修复：`fread` 少读一字节、显式写 `'\0'`、改用 `== NULL` 判空。

> **1 和 2 是上游普遍性缺陷**，与机型无关，任何较新 musl/glibc 环境都会复现，适合回馈上游。

## 3. 页码枚举错位（★ 一处错位制造四个症状）

`src/mcu_proto.h`

上游按「7 屏改造版」编址，而**原厂屏幕固件只有 5 页**。用扫描法（每 4 秒发一个页码
1→7，记录屏幕实际显示）测出真实映射：

| MCU 页码 | 实际内容 | 上游误定义为 |
|---|---|---|
| 1 | 型号 / 固件 / MAC | `PAGE_UPGRADE_INFO` |
| 2 | USB 与网口 | `PAGE_BASIC_INFO` |
| 3 | **速率 + WiFi 设备数** | `PAGE_PORTS` |
| 4 | WiFi SSID / 密码 | **`PAGE_WAN`** |
| 5 | 已接入终端 | `PAGE_WEATHER` |
| 6、7 | 不存在 | `PAGE_WIFI` / `PAGE_HOSTS` |

上游枚举多出 `PAGE_UPGRADE_INFO` 与 `PAGE_WEATHER`，使所有页码整体后移，于是：

- 按中键发页码 4 → 落到 **WiFi 密码页**（用户最早报告的现象，也是破案的关键线索）
- 站在速率页时程序以为在别页，`UPDATE_WAN` 数据发对了却不显示
- 按下一页要把 `g_current_page` 从 4 一路加到 7 才进设备页分支 → **要多按两次**
- 页码 6、7 发给只有 5 页的 MCU 直接无效 → 设备页成了「最后一页」

修复：枚举对齐 1–5，把本机不存在的两页移到有效区间之外（90/91），
`PAGE_MIN` 随之改为 `PAGE_BASIC_INFO`。

> **7 页机器请勿套用此补丁** —— 刷过新版斐讯官方/官改固件的机器屏幕固件较新，
> 上游枚举本就是对的。上游 README：「屏幕显示天气要以前刷过新版官方或官改固件，
> 屏幕固件是新版的才行」。

## 4. 切页时未重新采集

`src/pages.c`

周期刷新只更新 MCU 内部缓存、**不提交页面**（提交会叠字，见第 7 节），
因此屏幕数值完全取决于**切页那一刻**采集到的内容。上游 `page_switch_*` 只调
`page_refresh()`（发送上一轮数据）而不调 `page_update()`，导致切过去永远显示旧值。

修复：5 条切页路径均在发送前补上 `page_update()`。

## 5. 熄屏后仍满负荷采集

`src/signals.c`

`check_screen_timeout()` 只负责让 MCU 休眠，**不阻止后续采集**。实测黑屏后频率与亮屏一致：

```
熄屏前 40、31 次 ／ 熄屏后 46、52、26 次    （150 秒共 195 次）
```

修复后 120 秒 58 个周期中 **30 个被跳过**，熄屏期间采集与串口开销归零。
（顺带修掉超时后每周期重发 `EVENT_SLEEP` 的问题 —— 实测 64 秒发了 32 帧。）

## 6. MCU 复位产生的伪按键

`src/handlers.c` + `src/main.c`

`screen_initialize()` 拉动 `SCREEN_RESET_GPIO` 复位 MCU，MCU 在复位过程中吐出一帧：

```
01 30 03 | 10 04 00 00 00 | af 0b | 04
   ↑type=3    ↑转义后 = 04
   KEY_PRESS    KEY_RIGHT_SHORT
```

实测启动后约 1 秒必现、无人触碰按键。它被当成真按键处理，使页面从默认页自动跳走一页。
`serial_setup()` 里的 `tcflush` 发生在复位**之前**，拦不住。

修复：启动 3 秒内忽略按键，syslog 留痕 `ignoring key press during startup (MCU reset noise)`。

## 7. MCU 只在页码改变时清屏（关键约束与取舍）

**这颗屏幕固件收到相同页码只做增量绘制，新数字会叠在旧数字上。**

穷举过的提交方式，**全部叠字**：

| 尝试 | 结果 |
|---|---|
| 重发当前页码 | 数据会更新，但叠字 |
| 未知命令 `type=2` + 重发 | 叠字 |
| 未知命令 `type=3` + 重发 | 叠字 |
| 绕经无效页码 6 再切回 | 叠字 |
| `EVENT_WAKEUP` | 能让数据上屏，但不清屏 |
| `EVENT_SLEEP` + `EVENT_WAKEUP` | 叠字 |
| 重发全部 5 页数据后切页 | 叠字 |

唯一能触发清屏的是**页码真正发生变化** —— 所以左右翻页一直显示正常。

**由此得到硬约束：自动刷新与完全不闪，在这颗 MCU 上无法兼得。**

曾实现过「按间隔自动绕相邻页一趟重绘」，可以做到自动刷新，但每次重绘都有一次可见闪烁
（中间页停留 20ms 仍能察觉），实测干扰使用，**已移除**。

最终取舍：**周期只喂数据、不提交**（因此永不叠字），刷新交给按键。左右翻页页码必变、
本就正常；唯独第一页开机即停留、不翻页就不会刷新，故由中键补上：

```c
/* page_switch_to()：已在目标页时绕相邻页一趟制造页码变化 */
if (same_page) {
    PAGE detour = (page == PAGE_MIN) ? page + 1 : page - 1;
    request_switch_page(detour);
    usleep(DETOUR_DELAY_US);   /* 20ms */
}
request_switch_page(page);
```

> **绕行必须放在数据发送之后**。若夹在中间，采集（约 30ms）与数据发送都发生在绕行途中，
> 中间页实际停留远超设定值，会明显看到来回切页，MCU 还可能来不及处理而停在中间页。

彻底解决需升级屏幕固件（刷回斐讯官方/官改再刷回来），代价是重刷两次、配置清零。

## 走过的弯路（均已从源码彻底移除）

排查中基于代码推断打过 5 个补丁，事后证明都不是病因。如实记录：

| 曾经的改动 | 当时以为治什么 | 实际 |
|---|---|---|
| `main.c` poll 的 `else-if` 改独立 `if` | 定时器不触发 | 真实缺陷（串口忙时信号被跳过，而 `alarm()` 只在信号处理里重新武装），但**实测打不打都是 2.03 秒**，K3 串口负载不足以触发 |
| `frame.c` 接收端重写（63 行） | 「要多切几次才生效」 | 页码错位所致。**改动最大也最无谓** |
| `serial_port.c` 清 `ISTRIP` 等 | 数据被内核改写 | **方向错**：`c_iflag` 只管接收、发送归 `c_oflag`（`OPOST` 原本已清）。副作用还让接收更差 |
| `page_refresh()` 周期发 `SWITCH_PAGE` | 数据不重绘 | 页码错位时反复把画面拽向另一页，「闪烁」实为跳页 |
| 切页顺序改为「先切页后发数据」 | 设备页空白 | 与 `requests.h` 注释的配对语义相反，反而更糟 |

**教训**：

1. **先测出事实再改代码**。页码映射本可在第一轮用扫描法直接测出，却因一直在数据链路和
   帧协议层找原因而绕了很久。真正把方向掰过来的是用户一句「按中键显示的是 WiFi 密码」。
2. **精简改动时要重新评估每一处**。`page_update()` 曾被当作冗余删掉 —— 当时周期刷新还会
   提交页面，数据照样能上屏；后来改为「周期不提交」，它就从可有可无变成**唯一的数据来源**，
   症状是「能切页但数字不动」。
3. **区分「有实测背书」与「仅凭推断」**，并在文档中标注清楚。
