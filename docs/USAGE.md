# 使用与设置

## 按键

| 按键 | 行为 |
|---|---|
| **左 / 右短按** | 上一页 / 下一页 |
| **中键短按** | 回到并刷新**第一页**；已在第一页时会绕相邻页一趟强制刷新 |
| **中键长按** | 立即熄屏 |
| 任意键（熄屏时） | 唤醒，该次按键不触发翻页 |

> **为什么中键要「绕一趟」**：这颗 MCU 只在页码**改变**时清屏，收到相同页码只做增量绘制，
> 新数字会叠在旧数字上。左右翻页页码必变故一切正常；唯独停在第一页不动时无法自我刷新，
> 中键便通过短暂切到第二页再切回来制造一次页码变化。详见 [FIXES.md](FIXES.md) 第 7 节。

## 五个页面

| # | 内容 |
|---|---|
| 1 | 型号 / CPU 温度 / 负载 / 内存 / 运行时长（`showmore=1`）|
| 2 | USB 与网口连接状态 |
| 3 | WAN 上下行速率 + 2.4G/5G 客户端数 |
| 4 | WiFi SSID 与密码 |
| 5 | 已接入终端（每页 5 台，在该页按右键翻下一批）|

**页面不会自动刷新** —— 见 [FIXES.md](FIXES.md) 第 7 节的取舍说明。翻页即刷新。

## 第一页的显示规则

由 LuCI 的 **「显示更多信息」(`showmore`)** 决定，两套都是上游脚本自带的：

**`showmore = 1`**

| 行 | 内容 | 示例 |
|---|---|---|
| 1 | 产品名 | `K3` |
| 2 | CPU 温度 | `U:62 *C` |
| 3 | 负载 + 内存占用 | `U: 0.05 R:22%` |
| 4 | 运行时长 | `UP 3:45` |
| 5 | 系统版本（截断至 17 字符）| `ImmortalWrt 24.10` |

**`showmore = 0`**

| 行 | 内容 | 示例 |
|---|---|---|
| 1 | 产品名 | `K3` |
| 2 | 硬件版本（写死）| `A1` |
| 3 | 固件版本 | `r33869-cf234f8de6` |
| 4 | 固件版本（**上游就重复了一次**）| `r33869-cf234f8de6` |
| 5 | MAC 地址 | `D8:C8:E9:E4:50:D1` |

> 这五个槽位在协议里名为 `product_name`/`hw_version`/`fw_version`/`sw_version`/`mac_addr_base`。
> `showmore=1` 其实是**借用**这些字段塞温度、负载等，所以 `-t` 输出里会出现
> `HW Version = U:62 *C` 这种看似错位的内容 —— 是设计如此。
> 第 5 行受 `mac_addr_base[18]` 限制，最多显示 17 字符。

### 运行时长格式（本仓库已改）

| 运行时长 | 显示 |
|---|---|
| 9 分钟 | `UP 0:09` |
| 23 小时 59 分 | `UP 23:59` |
| 1 天 1 小时 3 分 | `UP 1d 1:03` |
| 2 天 23 小时 59 分 | `UP 2d 23:59` |
| 100 天 | `UP 100d 0:00` |

上游原写法是切 `uptime` 命令输出取字段，跨天后只显示 `up 2 days` —— 2 天 0 小时与
2 天 23 小时看着一样，精度掉到「天」。现改为直接读 `/proc/uptime` 计算，全程保持到分钟。

## LuCI 设置（系统 → Screen）

| 选项 | 生效 | 读取点 | 说明 |
|---|---|---|---|
| 熄屏时间 | ✅ | init 传 `-m` | 无按键多久后熄屏。**本仓库放宽了下限校验，可填 0 表示永不熄屏** |
| 刷新间隔 | ✅ | init 传 `-d` | 采集周期。**建议 2 秒**，见下方性能说明 |
| 隐藏 WiFi 密码 | ✅ | `wifi.sh` | 第 4 页密码显示为 `*` |
| 显示更多信息 | ✅ | `basic.sh` | 切换第一页的两套内容 |
| 设备名称 / 图标 | ✅ | `host.sh` | 给第 5 页的设备自定义显示名与图标 |
| Test 按钮 | ✅ | 执行 `-t` | 打印当前采集到的全部信息 |
| 天气：更新间隔 / 私钥 / 城市 / IP 定位 | ⚠️ | `weather.sh` | **5 页固件没有天气页，设了也看不到** |
| `pawd_hide` | ❌ | 无 | 死配置，无任何脚本读取，面板亦不显示 |

### 永不熄屏

```sh
uci set k3screenctrl.@general[0].screen_time=0
uci commit k3screenctrl && /etc/init.d/k3screenctrl restart
```

上游 init 脚本的 `[ $m -lt 10 ] && m=10` 会把 0 顶成 10 秒；本仓库改为
`[ "$m" != "0" ] && [ $m -lt 10 ] && m=10`，使 0 能透传（程序中 `screen_timeout==0` 即不熄屏）。

## 性能

采集脚本的单次耗时（conntrack 约 500 条时实测）：

| 脚本 | 耗时 | 2 秒周期占用 | 1 秒周期占用 |
|---|---|---|---|
| `host.sh`（设备页）| 127 ms | 10% | **21%** |
| `wifi.sh` | 114 ms | 5% | 11% |
| `wan.sh` | 70 ms | 3% | 6% |
| `port.sh` | 45 ms | 2% | 4% |
| `basic.sh` | 32 ms | 1% | 3% |

**只有当前页的脚本会跑**（上游设计），且**熄屏后完全不采集**（本仓库补充）。
刷新间隔设为 1 秒时设备页会持续吃掉约 1/5 的 CPU，建议保持 2 秒。

## 每设备速率的数据来源

`host.sh` 用 **conntrack 字节计数**统计每台设备的速率，而非 iptables/nftables counter。

原因：本机启用了软件 flow offloading，命中快速路径的包不再经过 nftables 的 forward chain，
基于 counter 的统计会漏计；而 `nf_flow_table` 会把字节数回写 conntrack（实测 15 秒增长
558079 字节）。**开启 offload 后 conntrack 是唯一仍然准确的 per-host 数据源。**

上游 README 也记录了「开启 HWNAT 或 offload 时 iptables 无法统计流量」，只是当年未找到替代路径。

> 另外：`flow_offloading_hw=1` 在 bcm53xx 上是**空开关** —— Broadcom 的 CTF/FastPath 闭源，
> OpenWrt 用开源 b53 驱动，所有接口 `hw-tc-offload` 命中 0 项。真正生效的只有软件 offload。
